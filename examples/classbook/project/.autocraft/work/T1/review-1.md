## Checklist result
1. Task and acceptance criteria: every T1 acceptance item is implemented and has a test (starts locally; bad config fails fast without secrets; migrations idempotent plus upgrade path; schema rejects capacity 0, duplicate active booking, second admin; exact 12h, day 30, +1 s, 30x24h across both DST changes; gap rejected, fold first; `write_tx` waits on a held lock; unhandled exception logged with request id and no secrets). Nothing extra beyond the declared `user_actions` table (F24) and the stricter CHECKs, which are declared.
2. Correctness: no logic errors found. Boundaries are exact: `is_bookable` is `now < start <= now+30*24h` (rules.py:34), `cancel_allowed` is `start-now >= 12h` (rules.py:47). `write_tx` uses autocommit plus explicit `BEGIN IMMEDIATE` (db.py:60-77), so contention waits and read-then-write has no lost updates (test_write_tx.py 20-thread test would fail with a deferred BEGIN).
3. Tests: they assert behaviour at the boundaries (not just run code). Constraint tests assert `IntegrityError` for each rule and the allowed counter-case (rebooking after cancel, many students).
4. Security: config errors never include values (config.py, tested with a sentinel in every field); `ADMIN_PASSWORD` is `repr=False`; parameterised SQL; migration stamp is the only f-string into SQL and is generated by the program. The 500 path logs exception type and frame locations only, not message, source or query string (logging_setup.py:79-83; tested with secret-bearing message and query).
5. Design fit: matches architecture s2/s3/s5 and ADR-0002. Declared deviations (write_tx takes a path; extra table; stricter CHECK; ADMIN_* required in all envs) are reasonable and I accept them.
6. Maintainability: small, readable modules, why-comments present, no dead code.
7. Operability/migrations: each migration is one transaction, failure rolls back and is unrecorded (tested), refuses a newer DB, takes a private `VACUUM INTO` copy before upgrading a DB that has data (mode 0600).
8. CI: cannot be observed here. See M-1.

## Findings

### [PRAISE]
- P-1 tests/test_rules.py and test_timeutil.py: boundaries are tested on both sides of every cut-off, including the "label disappears exactly at `opens_at`" case and both DST directions with the local-time consequence asserted (`26 10:00`, `06 08:00`).
- P-2 Error messages deliberately avoid values and a single test feeds one sentinel through all config fields.

### [MINOR]
- M-1 `.github/workflows/ci.yml`, `Dockerfile`: unrun workflow and image. By reading, they look correct (non-root user, one worker, `exec`, healthcheck uses `PORT`, `/data` created, `classbook/migrations` is inside the copied package, tzdata in requirements, CI container uses a writable `/tmp` DB path). Condition for the human merge: the first CI run (all three jobs) and a real `docker build` must be green; any failure there reopens this task.
- M-2 `ci.yml:11,26,32`: actions pinned by major tag only (`checkout@v4`, `setup-python@v5`, `gitleaks-action@v2`). Pin to commit SHAs when first verified, and expect `gitleaks-action@v2` to want a `GITLEAKS_LICENSE` secret if the repo is under an organisation; if so use the gitleaks binary instead. Unverified, as the developer already says.
- M-3 `requirements-dev.txt:4` `pip-audit==2.9.0` and `requirements.txt:17` `tzdata==2025.2` are unverified pins (the developer could not install them). Please confirm both resolve on a clean `pip install -r requirements-dev.txt` in python 3.13 and note it in the PR; the other pins match the venv I tested with.
- M-4 `kernel/db.py:58-77`: the architecture rule "read `now` once, after the lock is held" is only a docstring; `write_tx` cannot enforce it. Suggest yielding a small context (conn plus `now`) or a `tx.now()` helper in a later task so T4/T5 cannot read the clock before `BEGIN IMMEDIATE`. Not blocking T1; make sure the T5 brief says it explicitly and T5 has a test (the work breakdown already asks for one).
- M-5 `config.py:48`: unset `APP_ENV` silently means `development`, i.e. no `Secure`/`__Host-` cookies. A production deploy that forgets the variable fails open. T8's `render.yaml` must set `APP_ENV=production` (and the production check then forces `DATABASE_PATH` and `TRUSTED_PROXY_HOPS`). Add that to the T8 checklist, or consider `ENV APP_ENV=production` in the Dockerfile with local runs overriding it.
- M-6 `logging_setup.py:19-23`: redaction is by key name only, so a value passed under an innocent key (`log(..., detail=...)`) is not scrubbed. That is acceptable at this size, but state the rule ("never pass user data as a log field") in a code comment or the protocol, because T3 will log login events.

### [QUESTION]
- Q-1 `Dockerfile:8`: `/data` is chowned to `app`, but a host-mounted persistent disk normally replaces that directory with the mount's own ownership. Will the non-root user be able to write to the Render disk? Nothing to change now; T8 step 1 must prove this (deploy `/health` with the disk and create a DB on it) before anything depends on it. I could not verify Render's behaviour.

### [NIT]
- N-1 `migrations/0001_initial.sql` bookings: `cancelled_at` is not tied to `status` the way `cancelled_by` is. Optional extra CHECK `(status='booked') = (cancelled_at IS NULL)`; the test fixtures use `'x'`/`NULL` so adjust together.
- N-2 `rules.spots_left` can return a negative number after an admin lowers capacity below current bookings; T4 should decide how to display it (spec wording "full" at <= 0).
- N-3 `db.py:74-75`: if the `ROLLBACK` itself raised, it would mask the original exception; wrap in try/except and re-raise the original. Connection close would roll back anyway.
- N-4 `db.py` migration backups (`*.pre-vNNNN.bak`) are never pruned; fine now, mention it in the T8 runbook (they hold personal data).
- N-5 `Dockerfile`: no `--start-period` on HEALTHCHECK; unpinned base tag (`python:3.13-slim`) rather than a digest; pip installs without `--require-hashes`. All acceptable for phase 1.
- N-6 `tests/test_write_tx.py:27-40`: timing assertions (`0.8 <= waited < 4.5`) could flake on a very loaded CI runner; widen the upper bound if it ever does.
- N-7 `ci.yml`: add `timeout-minutes` to the jobs so a hung container step cannot run for hours.

No open BLOCKER or MAJOR. The MINORs are either to be tracked as follow-ups (M-4, M-5, M-6, Q-1 go into T5/T8 notes) or are verification steps on first push (M-1 to M-3). Branch protection and the human merge gate still apply: the human should not merge until the first CI run is green.
