# Architecture review – round 1
Verdict: CHANGES REQUESTED

## Summary
Reviewed independently: spec, architecture, API, work breakdown, threat model, ADR-0001..0005, the fullstack-app profile and the six capability files.
The design is sound where it matters most: the database is the referee for "last spot" races, spots-left is derived, and the 12-hour and 30-day boundaries are stated precisely. It is not ready to build yet.
In plain words for Maya: nothing here is wrong in spirit, but five gaps would cause rework or a real weakness if we start coding now (a sign-in flow that does not work as the spec promises, the "one admin" rule not being enforced, a login-protection design that can lock you out on a hosted machine, three parallel tasks that secretly share rules, and no early test of the hosting). None needs a decision from you except the two marked HUMAN DECISION. Zero BLOCKERs, five MAJORs; approval needs the MAJORs resolved.

## Findings

### Major (must fix before approval)
- [MAJOR] F1 – AC-2.3 is not met by the API design (`api.md` #5, #2/#3, `next` rule). Booking is POST-only (`POST /classes/{id}/book`) and there is no class page. A visitor's click leads to `/login?next=/classes/7/book`; after login the browser does a GET of a POST-only URL (405), so the visitor does not "return to that class". Also a signed-out visitor has no session, so no CSRF token for that POST (see F2). Fix: show visitors a "Sign in to book" link to `/login?next=/%23class-7` (or add a `GET /classes/{id}` page with the Book button) and say which one; add the test "visitor -> login -> lands on that class, can book".
- [MAJOR] F2 – CSRF is undefined before a session exists (`architecture.md` s5, `api.md` conventions say "all POSTs require `csrf_token`", but the token lives in the `sessions` row). `POST /login` and `POST /signup` are made by people with no session, so T2 cannot implement the rule as written (login CSRF / forced login to attacker's account is a known attack). Fix: define a pre-session mechanism (e.g. a signed or random double-submit cookie for anonymous forms, rotated at login), and say how a single template helper (in T1) emits the hidden field for every form so T3/T4 forms get it. Add a test that every POST form in every template contains the token.
- [MAJOR] F3 – The "single admin" invariant and the bootstrap are under-specified and can leave a stray admin (`architecture.md` s5 "created/updated from env at startup"; spec s2 "single admin account"). Gaps: (a) if `ADMIN_EMAIL` is changed later, the old account keeps `role='admin'`; (b) if a student already signed up with that email, "update" silently promotes them and overwrites their password; (c) nothing in the schema stops a second admin. Fix: add a unique partial index (`role='admin'` -> at most one row), and define startup behaviour precisely: create if no admin exists; if the admin's email differs from env, demote or refuse to start with a clear message; never promote an existing student without an explicit flag; document that changing `ADMIN_PASSWORD` resets the admin password. Add tests for each case. (T-2 depends on this being right.)
- [MAJOR] F4 – Login throttle design is not safe on the intended host (`api.md` #3, `architecture.md` s5/s6, T-4, T-15). It is keyed by (email, IP) and held in memory, but behind a platform proxy the app sees the proxy's IP (every user shares one key, so five typos from anyone lock Maya out) unless it trusts `X-Forwarded-For` (which a client can spoof, defeating the limit). Also a distributed attacker rotating IPs against the admin email faces no cap, and the counter resets on every restart/deploy. Fix: state how the real client IP is obtained (trusted proxy header from the known platform only), add a per-email (not just per-email+IP) failure cap with a gentle backoff, and store the counters in SQLite or accept and document the restart reset. Say what the sign-up throttle keys on. Test with forwarded-header spoofing.
- [MAJOR] F5 – T2/T3/T4 are not truly independent, and the cross-task tests have no owner (`work-breakdown.md` header and T2-T4). Three things are needed by more than one of them but are not defined in T1: (a) the **30-day window predicate** and **spots-left query**: T3 builds the schedule listing, T4 builds the booking check; if each writes its own, the schedule and the booking rule can disagree at the day-30 edge (AC-3.6/3.7); (b) the **write-transaction helper** (`BEGIN IMMEDIATE` with the Python `sqlite3` autocommit setting that makes it work, with busy_timeout -> 503); T3 (capacity-lowering, class cancel) and T4 (book/cancel) each need it, and in WAL mode a read-then-write transaction not started as IMMEDIATE fails at once with "database is locked" instead of waiting; (c) the **CSRF/flash template helpers** (F2). Also, T3/T4 test with role overrides and T2 tests auth alone, so nothing checks the real combination: the "every non-public route has a guard" test (T-2) and the full authz matrix (anonymous/student/admin/other-student on every route) cannot pass or even exist until all three are merged, and T6 only lists a happy-path journey. Fix: move (a)-(c) into T1 as small shared modules with unit tests (T3/T4 import them, never re-implement), and assign the route-guard test and authz matrix to a named task after T2-T4 merge (e.g. T5 or a new T5b), listed in its acceptance criteria.
- [MAJOR] F6 – No walking skeleton that actually deploys, and the riskiest assumption is checked last (`work-breakdown.md` T1/T6, `architecture.md` R4, ADR-0005; fullstack-app profile says task 1 deploys to a preview URL with one E2E test). The whole design depends on a host with a persistent disk and a single writer (SQLite), yet the host decision is a gate only "before T6", after five tasks of code. If the host cannot do it, the data layer changes late. T6 is also overloaded (Dockerfile, backups, restore, logging, E2E, a11y, runbook). Fix: put a minimal Dockerfile + deploy of `/health` with a volume into T1 (or a T1b right after), move the host choice (HUMAN DECISION, see F14) to before T2, move JSON logging with request id into T1 (T2 and T5 already test log content), and split T6 into delivery/backup/runbook vs E2E/a11y.

### Minor (should fix; may be tracked as issues)
- [MINOR] F7 – ADR-0003 deviation: my decision. The capability says "don't build password hashing or sessions yourself". I accept the deviation for phase 1, conditionally: `hashlib.scrypt` (OpenSSL-backed) with per-user salt and `compare_digest` is a vetted primitive rather than invented crypto, the session design (random 256-bit token, hash stored, server-side expiry and logout) is simple and standard, and a hosted provider or extra libraries add cost/accounts for one studio. The justification "no new dependency" is weak (six dependencies are already added), so the ADR should rest on the real reasons (no mail service for verification/reset, single admin, tiny budget). Conditions: (1) pick and record scrypt parameters (memory-bound; roughly N=2^14, r=8, p=1) and cap password length (e.g. 128) so 50 simultaneous sign-ups cannot exhaust a small machine's memory; (2) hash/verify **outside** any write transaction; (3) run a dummy hash on unknown emails so login timing does not reveal accounts; (4) versioned hash prefix as planned; (5) list "no MFA for the admin" as a named risk (see F15). Update the ADR text "Principal-engineer to confirm" to record this outcome.
- [MINOR] F8 – Rule precedence for refusals is unspecified (`api.md` #5, #7). If a student already booked a now-full class, do they see "already booked" or "full"? What if a class is cancelled, started, and full at once? Define one fixed order (suggested: unknown -> cancelled/started -> too far ahead -> already booked -> full) and test it. Same for cancel (not mine/404 -> already cancelled -> too late). Also read `now` once, inside the transaction after the lock is held, and use that single value for every comparison in the request.
- [MINOR] F9 – Time edge cases (`architecture.md` s3, s8). "30 days" should be defined as exactly 30x24 hours from now in UTC, not calendar days, so DST changes do not move the boundary (state it). Admin-entered local times that do not exist (spring-forward gap) or occur twice (autumn fold) in Europe/London need a defined result (reject the gap, pick the first occurrence for the fold) and a test; the T1 DST test covers only conversion. Edit (#11) must also reject moving a start time into the past.
- [MINOR] F10 – Email details (`ADR-0004`, `architecture.md` s3/s6). (a) Who writes the `messages` row when the mailer itself is the thing that fails? Define: the service inserts a `pending` row after commit, the mailer sends, the row is updated to `recorded`/`failed`. (b) The unique `(booking_id, kind)` plus a `failed` row blocks a later retry; note it as part of the outbox upgrade. (c) A student can book/cancel in a loop, creating unlimited messages (every rebook is a new booking id): add a per-user cap on mail-triggering actions before real delivery. (d) Reject newlines/control characters in title, name and instructor so subjects cannot be header-injected later. (e) Because there is no email verification, anyone can sign up with someone else's address and the confirmation, containing an attacker-chosen name, would reach the victim: add an explicit rule to ADR-0004 and the threat model that real delivery must not be enabled until verification exists.
- [MINOR] F11 – Session and cookie details (`architecture.md` s5). `Secure` is controlled by both `APP_ENV=production` and `SESSION_COOKIE_SECURE`; keep one, defaulting to secure in production. Expired `sessions` rows are never purged (add a cleanup at startup). `next` validation must also reject backslashes (`/\evil.com`), control characters and encoded slashes, not just `//` and schemes (T-9, unit test list). Consider the `__Host-` cookie prefix.
- [MINOR] F12 – Input limits and email format are not specified (all forms). Add maximum lengths (name, email, title, instructor), a basic email-shape check, lowercase normalisation (stated) and a request body size limit, with tests; stops oversized data and abuse of the roster page.
- [MINOR] F13 – Backups are described but not runnable (`ADR-0005`, `architecture.md` s6, T-12/T-13, secrets list). Missing: what actually runs the nightly job on a one-machine host, where the off-box copy goes, the credential for it (not in the `config` env list, so secrets-and-config is incomplete), and whether the copy is encrypted (it holds password hashes and personal data). Also define account deletion (R5): delete versus anonymise the user's bookings, and note that deleted people remain in the 14 backups until they age out. Consider a continuous-replication tool for SQLite rather than only a nightly copy; at least pick one in the ADR before T6.
- [MINOR] F14 – Observability is below the capability's defaults (`architecture.md` s5). Error tracking is deferred as an "assumption" and nobody is named to receive an uptime alert. Phase 1 logs-only is acceptable for this size, but record who gets the `/health` alert (email to Maya or the owner), what she does when it fires (runbook line), and add one test that an unhandled exception is logged with request id and no secrets.
- [MINOR] F15 – Admin protection (`threat-model.md` residual risk). A single admin who can see every student's name and email has no MFA and no reset, behind a throttle (F4). Accepting this for phase 1 is reasonable, but it is a risk acceptance and must be made visible to the human, not left in a footnote (see Q1). Cheap extra: enforce a longer minimum for `ADMIN_PASSWORD` (e.g. 14) and show the admin a "last sign-in" note.
- [MINOR] F16 – Task sizing and ordering (`work-breakdown.md`). T1 (config, DB, migrations, seams, CI with three scanners, base template, health) and T2 (accounts, sessions, CSRF, throttle, bootstrap, headers) will each exceed the 400-line PR limit; split (T1a seams/config/DB, T1b CI/deploy; T2a accounts/sessions, T2b CSRF/throttle/headers). The 50-thread test uses threads in one process; add one booking race through real HTTP against uvicorn in T6, and run the same concurrency test against the exact SQLite settings (`synchronous`, WAL) that production uses, stated explicitly.

### Nit

- [NIT] F18 – "My bookings" hides bookings the admin cancelled; consider showing them as "cancelled by the studio" (still no email, per Q5), so a student is not left wondering. Not required by the spec; mention only.

## Traceability check (spec to design)
All AC-1.x to AC-6.x map to a route in `api.md` and a task. Gaps found: AC-2.3 (F1); AC-2.x signup/login CSRF (F2); "single admin" (F3). Nothing found that nobody asked for. Concurrency AC-3.3, AC-6.2, AC-4.5 and boundaries AC-3.6 (`start <= now+30d` allowed, one second later refused) and AC-4.2/4.3 (`start - now >= 12h`) are correct as written, subject to F5, F8, F9.

## What is good
- The concurrency story is correct and simple: derived spots-left, `BEGIN IMMEDIATE` so check and insert cannot interleave, a partial unique index as a second guard for AC-3.4, and a rejected alternative (in-process lock) that explains why the database must be the referee. A 50-thread test is required, including book-vs-cancel and capacity-lowering races.
- Boundaries are written down precisely (exactly 12 hours allowed, day 30 allowed, day 30 plus one second refused), stored as UTC and displayed in London, with the rule constants in one module and an injectable `Clock`.
- Authorization is server-side and by ownership in SQL (user id from the session, never the browser), foreign bookings answer 404, and the threat model includes a test that walks every route; the threat model is specific to this app (IDOR, enumeration residual, open redirect, backups as an asset), not boilerplate.
- Email-after-commit is handled correctly: sent only by the code path that actually changed a row, deduplicated twice (no-op path plus unique constraint), failure cannot undo a booking, and the crash-loses-one-email trade-off is stated honestly in ADR-0004.
- Good restraint: no queue, ORM, SPA or JSON API; every deviation from the capabilities (SQLite, hand-rolled sessions, no verification) is declared in an ADR with alternatives and an upgrade path.
- Rollback and migrations are thought through (additive-only, backup before migrate), and the plain-language summary for Maya is clear.
