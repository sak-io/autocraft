# Security audit: ClassBook, 2026-10-10

Auditor: `security-auditor`. Scope: branch `main` at `02d2362` (T1-T6 integrated; T7 QA and T8 ops not yet merged). Code was read in full (about 2,000 lines of Python, 14 templates, Dockerfile, CI file, migration) and probed in a throwaway copy outside the project folder. Nothing in the project was changed except this report.

## 1. Summary

| Severity | True positive | Accepted risk / informational | False positive |
|---|---|---|---|
| CRITICAL | 0 | 0 | 0 |
| HIGH | 0 | 0 | 0 |
| MEDIUM | 3 | 0 | 0 (4 scanner hits, section 4) |
| LOW | 7 | 5 | 0 |

Verdict: no way found to read another student's data, become admin, bypass CSRF, steal a session, inject script or SQL, or leak a secret. The three MEDIUM items are (M-1) the backup/restore and admin-download features are not built yet, so going live now would leave data loss and personal-data handling unprotected; (M-2) the sign-up throttle can be used to fill the disk; (M-3) the per-IP login limit would lock everyone out if the proxy setting is wrong on Render. M-1 is already planned in T8; M-2 and M-3 need a small fix or check before go-live. Recommendation: do not deploy to real users until M-1 to M-3 are closed.

## 2. Findings

### M-1 [MEDIUM] Backups, admin download and nightly copy do not exist yet (T-12, T-13)
- Status: true positive (planned work, T8, not a regression).
- Location: `docs/architecture/api.md` row 14 (`GET /admin/backup`); no route in `classbook/routes/`; no nightly job; no `render.yaml`; no deletion script.
- Evidence: `grep -rn backup classbook` finds only the migration safety copy in `classbook/kernel/db.py:112-117`. Probe: `GET /admin/backup` returns 404 for anonymous and for a student.
- Impact: until T8 the only copy of all bookings is one SQLite file; a disk fault or bad deploy is unrecoverable. T-12 and T-13 are documented as mitigated but are not.
- Fix: build T8 as written: nightly `VACUUM INTO`, admin-only `no-store` download deleted after send, render.yaml, restore rehearsal, deletion script. Add a test that student and anonymous get 403/303 on the download.

### M-2 [MEDIUM] Throttled sign-up attempts are still written to the database (A5 availability, T-15)
- Status: true positive.
- Location: `classbook/routes/accounts.py:86-91`, `classbook/auth/service.py:41-46`.
- Evidence: `signup()` inserts a `signup:<ip>` row for every request and only then checks the count. Probe: 61 POSTs to `/signup` returned 10 normal answers and 51 x 429, and left 61 rows in `login_failures`. Rows are only purged at start-up or once a day after a successful login (`_maybe_purge`, accounts.py:36-41).
- Impact: an unauthenticated client can append rows as fast as the server answers (roughly 200 per second on a small instance). Each row needs a write lock, so bookings slow down, and the 1 GB disk (ADR-0005) can fill within about a day, after which every write fails. Per-IP limit does not help because throttled requests still record.
- Fix: count first, record only when under the cap (or stop recording once the count is already at the cap). Also purge `login_failures` from a small timer, not only after a login. Add a test that 200 throttled sign-ups leave at most `SIGNUP_CAP + 1` rows.

### M-3 [MEDIUM, conditional] Wrong proxy-hop setting would make one shared IP key lock everybody out (T-4, T-18)
- Status: true positive as a deployment risk; cannot be confirmed without Render (T8).
- Location: `classbook/web/util.py:34-50`, `classbook/auth/service.py:36-38`, `Dockerfile` last line.
- Evidence: `client_ip` takes the right-most `X-Forwarded-For` entry for `TRUSTED_PROXY_HOPS=1`. If Render puts a second proxy or CDN hop after the real client (the architecture assumes one), that entry is the proxy's address, shared by all visitors. Then 20 failed logins from anyone in 15 minutes trips the per-IP cap for everyone, including Maya. The sign-up cap (10 per hour per IP) would also be shared by all new students.
- Impact: whole-site login/sign-up denial by one person with 20 bad passwords; or, if the setting is 0 in production, the same effect through the socket address (the app also refuses to start in production without the variable, config.py:89-90).
- Fix: in T8 step 1, deploy a build that logs (redacted) the number of `X-Forwarded-For` entries, confirm the entry at position N-from-right is the visitor, then fix `TRUSTED_PROXY_HOPS`. Add this check to the runbook.

### L-1 [LOW] Oversized or non-numeric ids give 500 or JSON 422 instead of 404
- Status: true positive (robustness, not exploitable).
- Location: `classbook/services/bookings.py:74` and `:105` (queries with the id), `classbook/routes/bookings.py:51,78`; `classbook/routes/classes.py:75` etc. (`class_id: int`).
- Evidence: `POST /classes/99999999999999999999999/book` and `POST /bookings/99999999999999999999/cancel` returned 500 (SQLite `OverflowError`; T4 fixed this only in `get_class`). `GET /classes/abc` returns FastAPI's default JSON 422 that echoes the input string, not the HTML 404 that api.md promises. The 500 page is generic and logged without data, so no leak.
- Fix: catch `OverflowError` in the two service queries (treat as NOT_FOUND) and add a handler that turns `RequestValidationError` on path parameters into the normal 404 page. Add tests.

### L-2 [LOW] Password hash cost is below current guidance
- Status: true positive (hardening). ADR-0003 chose N=2^14, r=8, p=1 and did not weigh this.
- Location: `classbook/auth/passwords.py:10`.
- Evidence: one hash takes about 47 ms on this machine. OWASP's password-storage guidance lists N=2^17 (r=8, p=1) or equivalents such as N=2^16, p=2 as the minimum. Hashes live in the database and in every backup (asset A6), so cost matters only if a backup leaks, but then it matters a lot for 10-character student passwords.
- Fix: add `scrypt2$` (for example N=2^16, r=8, p=2, `maxmem` raised) and re-hash on successful login; keep `scrypt1` verifiable. Re-check memory on the Render Starter size (about 64 MB per concurrent hash) and keep the existing per-IP login cap.

### L-3 [LOW] Some tables are never cleaned, and the messages table keeps email addresses forever (T-13)
- Status: true positive.
- Location: `classbook/auth/service.py:83-85` (`purge_expired` handles only sessions and login failures); tables `user_actions`, `messages` in `0001_initial.sql`.
- Evidence: no `DELETE FROM user_actions` or `messages` anywhere. `user_actions` grows by up to 20 rows/hour/user; `messages` stores `to_email`, subject and body of every confirmation.
- Fix: purge `user_actions` older than 1 day alongside the others; decide a retention period for `messages` (suggest 90 days) and cover both in the T8 deletion script and runbook.

### L-4 [LOW] Supply-chain checks are thin and the CI file has never run
- Status: true positive.
- Location: `.github/workflows/ci.yml`; no `.github/dependabot.yml`, `SECURITY.md`, `CODEOWNERS`.
- Evidence: the file's own first line says it was written without being run. `pip-audit` audits `requirements.txt` only, and only on pushes, so a new vulnerability published next month is not noticed. No SAST (bandit or CodeQL) step. Actions are pinned by tag (`actions/checkout@v4`, `gitleaks/gitleaks-action@v2`), not by commit. Branch protection cannot be verified without GitHub.
- Fix: add Dependabot for pip and GitHub Actions, add the scheduled workflow from `.autocraft/templates/github/workflows/security-scheduled.yml`, add `bandit -r classbook -ll` and CodeQL, pin actions by SHA, copy the SECURITY and CODEOWNERS templates, and confirm on the first push that all three CI jobs go green and branch protection requires one approving review.

### L-5 [LOW] Content-Security-Policy and HSTS could be tighter
- Status: true positive (defence in depth only; no exploit found).
- Location: `classbook/web/middleware.py:17-24`.
- Evidence: CSP is only `default-src 'self'`. `form-action`, `base-uri` and `frame-ancestors` do not fall back to `default-src`. Framing is already blocked by `X-Frame-Options: DENY`. HSTS has no `includeSubDomains`.
- Fix: `default-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`; add `includeSubDomains` only if the host serves nothing else on subdomains.

### L-6 [LOW] Container build is not reproducible
- Status: true positive.
- Location: `Dockerfile:1-4`.
- Evidence: `python:3.13-slim` is a moving tag, and `pip install -r requirements.txt` has pinned versions but no `--require-hashes`. The container runs as a non-root user and excludes `.env`, `.git`, tests and database files via `.dockerignore`, which is good.
- Fix: pin the base image by digest (Dependabot can update it) and generate hashed requirements (`pip-compile --generate-hashes`). Also in T8 step 1 (open question Q-1): prove the non-root user can write to the Render disk mounted at `/data`.

### L-7 [LOW] Migration safety copy is briefly world-readable
- Status: true positive (minor).
- Location: `classbook/kernel/db.py:116-117`.
- Evidence: `VACUUM INTO` creates the `.bak` file with the process umask, then `os.chmod(0o600)` runs. In between, the file (which holds personal data and password hashes) has default permissions. In the container only the `app` user exists, so impact is negligible.
- Fix: set `os.umask(0o077)` at start-up (Dockerfile or `create_app`) so the database, its `-wal` files and copies are private from the first byte.

## 6. What this means for Maya

1. Nothing found lets a stranger see other students' details, book on someone else's behalf, or become the admin; the sign-in and booking code held up when I tried to break it.
2. Do not open the site to real students yet: the automatic daily backup and the "download a copy" button are not built, so one server fault could lose every booking. That is planned work (step 8) and is the main thing standing in the way.
3. Someone could fill the studio's storage by hammering the sign-up page, and a wrong setting on the hosting site could make the login block everyone after a few mistakes; both are small fixes the developer will make and test before launch.
4. Your admin password is the one lock on all student names and emails, as you agreed: keep it long, never share it in chat or email, and glance at the "previous sign-in" time on the admin page to spot anyone else.
5. You need to do nothing right now; when Tom signs up for the host, he must run one quick check of the visitor-address setting, and the repository should be put on GitHub so the automatic safety scans can start.
