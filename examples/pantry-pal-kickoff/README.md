# Rehearsal: kick off a project from your own documents

This is the scenario from [Kick off a project from your own documents](../../docs/kickoff-existing-docs.md), rehearsed with real agents. A fictional owner has a **product concept** and a **technical plan** in a repo (`inputs/`), adds the small `CLAUDE.md` pointer, and says *"Kick off this project with autocraft."*

> **What this is and isn't.** The agents were real and separate, and they read only what a fresh session would see (the repo + pointer). It ran in a cloud Code session like the Claude app's, but **not through the app's phone UI**, and the repo had **no GitHub remote** (so pushing and `add_repo` of a private framework repo were not exercised). The documents were written to contain deliberate gaps and contradictions to see whether the team finds them.

## Inputs (`inputs/`)
- [`product-concept.md`](inputs/product-concept.md) and [`technical-plan.md`](inputs/technical-plan.md) — "Pantry Pal", a shared grocery/pantry app for households.
- [`CLAUDE.md`](inputs/CLAUDE.md) — the pointer (generated by `autocraft pointer`).
- Planted problems: *offline use* promised vs. *30-second polling* planned; a *Premium plan* with no payments design; *pantry data sent to an AI provider* vs. "visible only to its members"; *testing "after the first release"*; "push notification" for a website; no scale or cost numbers.

## Step 1 — the Team Builder (51 seconds, ≈28k tokens)
Given only the owner's one sentence, the real `team-builder` agent read the pointer and both documents, ran `recommend`, and answered the way a good lead would. Excerpts of its reply to the owner:

> **Recommendation: the LEAN team, plus two extra helpers** … I'd add [`architect`] to check your technical plan, keep your choices, fill missing parts … and [`qa-engineer`] … Your plan says testing comes "after the first release". For an app that stores family data and has a "visible only to members" promise, I don't think that is safe. Tests are built in from the start.
>
> **Problems I noticed in your documents (my honest view, you decide):** 1. Magic-link sign-in needs real email, but you said no real emails in v1 … 2. **Offline use (feature 6) conflicts with "poll every 30 seconds, no websockets".** Polling alone does not make the list work offline … 3. Push notifications … need a scheduler … 5. **"What can I cook?" sends pantry data to the Claude API.** That touches your principle "we never sell household data" … 6. Row-level security … must be tested thoroughly, because one mistake would show a family's data to another.

It then installed the team (`autocraft init … --team starter --add-role architect,qa-engineer --sources …`), ran `doctor` (OK), and committed on the session branch: 6 role agents, 8 commands including `/kickoff`, `.claude/settings.json`, CI and security templates — ≈177 files, most of them the one-time framework copy.

## Step 2 — the spec, in ingest mode (109 seconds, ≈73k tokens)
The `requirements-analyst` produced [`outputs/spec-pantry-pal.md`](outputs/spec-pantry-pal.md): **10 user stories** with Given/When/Then criteria, **each citing the section of the owner's document it came from** (or marked `ASSUMPTION`), non-goals, non-functional needs — and **22 gaps, ambiguities and contradictions** (4 blocking), each with a recommended default so work could continue. It found every planted problem, plus ones that weren't planted, for example:

> **G16 [MAJOR]** Two access paths to data: REST routes inside Next.js and row-level security in Supabase. If routes use the Supabase service key, row-level security is bypassed and one household could read another's data. *Default:* routes act as the signed-in user; service key only for the scheduler; two-household tests.

The owner would now see five plain questions (offline scope, reminders, sending pantry names to an AI, billing in v1, tests from day one) and reply "default" or correct them. The architect (adopt mode) goes next.

## What the rehearsal found wrong with autocraft (all fixed in this change)
| Finding | Fix |
|---|---|
| The pointer didn't say which `--tool` to use in the Claude app, or what to do when there is no remote | Pointer states `--tool claude-code` covers app sessions; "no remote → just commit" |
| The pointer didn't map the interview to flags (`--experience`, `--autonomy`, `--add-role`) | It does now, including who the owner is (`--owner`, new) |
| "Lean" had no architect, but a project arriving with a technical plan needs one | Documented: lean for kickoff = `starter` + `architect` (+ `qa-engineer` for personal data) |
| `recommend --file` was noisy and missed the real risks (AI, offline, notifications, scheduling) | Collapses overlapping types, lists "also mentioned" parts, and prints design-risk flags |
| The team passed `--lang node` and installed CI before any plan existed | Pointer: don't pass `--lang`; CI/GitHub hardening comes after plan approval |
| 880 KB of framework copied into the repo with no explanation | Explained to the owner as a one-time copy so later sessions don't need autocraft access |
| `doctor` said "OK" without checking much | Now also checks source documents exist and notes a missing owner handle |
| `settings.json` pre-approves commands, which a beginner should be told | The Team Builder now tells the owner, in plain words |

## Not yet proven
- Starting the session from the Claude **app on a phone**, and the session obtaining the private `sak-io/autocraft` repo (`add_repo`) — the pointer handles both, but they have not been exercised.
- The rest of `/kickoff` on this project (plan, build, QA, release). The [ClassBook example](../classbook/README.md) shows those stages on a different project.
- `autocraft`'s `main` branch must contain the framework (it currently lives on the work branch) before a fresh session can clone a working copy.
